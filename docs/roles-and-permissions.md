# Roles, callers and permissions

This document maps the access model implemented in the current checkout. It is
about code-level rules, not a deployment registry: it does **not** identify who
holds any role on any live chain. A live-state claim must separately name the
network, factory or vault address, block, ABI matching that deployment, and the
on-chain reads used as evidence.

The vault execution and `delegatecall` boundaries are described in
[`architecture.md`](architecture.md). The sources of truth for permissions are
the factory's modifiers in [`FusionFactory.sol`](../contracts/factory/FusionFactory.sol),
the vault role constants in [`Roles.sol`](../contracts/libraries/Roles.sol), and
the target/selector and administrator mappings generated by
[`IporFusionAccessManagerInitializerLibV1.sol`](../contracts/vaults/initializers/IporFusionAccessManagerInitializerLibV1.sol).

## Keep the identities separate

| Identity                       | Meaning in the current factory flow                                                                                                                                              | Does it select the creation-time fee package?                                                |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Factory administrator          | Account with the factory's OpenZeppelin `DEFAULT_ADMIN_ROLE`; the initializer grants it to `initialFactoryAdmin_`. It can administer factory roles and authorize a UUPS upgrade. | Only if that same address is the direct caller of `clone` or `cloneSupervised`.              |
| Direct factory caller          | `msg.sender` at the `FusionFactory` proxy. `clone` is public; `cloneSupervised` additionally requires `MAINTENANCE_MANAGER_ROLE`. Library delegatecalls preserve this sender.    | **Yes.** Client-specific packages are looked up under this address.                          |
| Requested vault owner          | The nonzero `owner_` argument. The new vault's AccessManager grants this address `OWNER_ROLE`.                                                                                   | No. Passing an address as `owner_` does not make that address the factory caller.            |
| Supervised-vault administrator | For `cloneSupervised`, the direct factory caller is also placed in the new AccessManager's `ADMIN_ROLE`. Plain `clone` supplies no vault administrator.                          | The address selects fees because it is the caller, not because it becomes an administrator.  |
| Effective vault caller         | Normally `msg.sender`; when a call is made through the vault's approved `ContextManager`, the signed or forwarded context sender is used by `_msgSender()`.                      | Not applicable after creation; it is the identity checked against the vault selector's role. |

These assignments follow the factory entry points and `withAdmin_` flag in
[`FusionFactory.sol`](../contracts/factory/FusionFactory.sol), the preserved
`msg.sender` and `owner_` handling in
[`FusionFactoryLogicLib.sol`](../contracts/factory/lib/FusionFactoryLogicLib.sol),
and the effective-sender implementation in
[`ContextClientStorageLib.sol`](../contracts/managers/context/ContextClientStorageLib.sol).
The AccessManager clone temporarily gives the FusionFactory authority so the
factory can configure it; `initialize` then revokes that temporary admin before
granting the final accounts from the generated configuration. See
[`AccessManagerFactory.sol`](../contracts/factory/AccessManagerFactory.sol) and
[`IporFusionAccessManager.sol`](../contracts/managers/access/IporFusionAccessManager.sol).

### The caller selects the fee package

Both creation entry points accept a package **index**, but the array behind that
index depends on the direct factory caller:

1. `FusionFactoryLogicLib._validateAndGetDaoFeePackage` checks the business-client
   package array stored under `msg.sender`.
2. If that caller has a non-empty custom array, the supplied index is resolved
   only against that array.
3. Otherwise the index is resolved against the global DAO package array.
4. The selected management fee, performance fee and recipient are passed into
   the new vault's fee configuration.

The lookup and fallback are implemented in
[`FusionFactoryLogicLib.sol`](../contracts/factory/lib/FusionFactoryLogicLib.sol);
package administration and the public preview-style
`getBusinessClientFeePackages(client_)` getter are in
[`FusionFactory.sol`](../contracts/factory/FusionFactory.sol). Tests exercise a
business caller, an unrelated caller and a supervised maintenance caller in
[`FusionFactoryBusinessClientFeePackagesTest.t.sol`](../test/factory/FusionFactoryBusinessClientFeePackagesTest.t.sol).

Operational consequence: an EOA, Safe or forwarding contract is a different
package identity whenever it is the address that directly calls the factory.
Before constructing calldata, query packages for that exact caller and validate
the index against the returned array. Do not query for `owner_` unless `owner_`
will also be the direct caller. A relayer or wrapper does not inherit the
originating user's custom package merely because it forwards the same `owner_`.

## FusionFactory roles

The factory uses OpenZeppelin `AccessControlEnumerableUpgradeable`, not the
per-vault `IporFusionAccessManager`. Its current permission surface is:

| Factory role               | Current code-level authority                                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DEFAULT_ADMIN_ROLE`       | Granted to `initialFactoryAdmin_`; administers factory role membership through inherited AccessControl functions and gates `_authorizeUpgrade`.                                            |
| `MAINTENANCE_MANAGER_ROLE` | Calls `cloneSupervised`; updates component factory addresses, clone base addresses, the PlasmaVault base, price oracle middleware, burn-request fuses, withdraw window and vesting period. |
| `DAO_FEE_MANAGER_ROLE`     | Replaces global DAO packages and sets or removes caller-specific business-client packages.                                                                                                 |
| `PAUSE_MANAGER_ROLE`       | Declared in `FusionFactoryAccessControl`, but the current `FusionFactory` exposes no `pause` or `unpause` entry point and therefore attaches no current permission to this role.           |
| No factory role            | May call plain `clone` and all public getters.                                                                                                                                             |

The role constants are in
[`FusionFactoryAccessControl.sol`](../contracts/factory/FusionFactoryAccessControl.sol);
the table above is checked against every current `onlyRole` use in
[`FusionFactory.sol`](../contracts/factory/FusionFactory.sol). No delay or
scheduling layer is added to these factory checks. Initializing the factory only
grants `DEFAULT_ADMIN_ROLE`; maintenance and fee-manager membership must be
granted separately. This describes source behavior only, not current members of
an existing factory.

## Per-vault AccessManager

Each factory-created vault receives its own `IporFusionAccessManager`. Restricted
entry points ask that authority for the role assigned to the target address and
function selector. The factory-generated vault is private initially, so deposits
and mints require `WHITELIST_ROLE`; withdrawals, redemptions and
`redeemFromRequest` use `PUBLIC_ROLE`. Deposit and mint check both the effective
caller and share receiver, while withdraw and redeem check both the effective
caller and share owner. The exact branches are in
[`PlasmaVault.sol`](../contracts/vaults/PlasmaVault.sol), and the initial selector
mapping is in
[`IporFusionAccessManagerInitializerLibV1.sol`](../contracts/vaults/initializers/IporFusionAccessManagerInitializerLibV1.sol).

the selector-level source.

### System-assigned and technical roles

Technical roles restrict cross-component calls rather than identify human
operators. During factory setup they are granted with zero execution delay to
the concrete vault, FeeManager, RewardsClaimManager, ContextManager and
WithdrawManager addresses. The selected fee recipient also receives the
self-administered `IPOR_DAO_ROLE`. These assignments cover:

| Technical role                                                             | Factory-assigned holder and purpose                                                                           |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `TECH_PLASMA_VAULT_ROLE`                                                   | PlasmaVault; calls protected functions on AccessManager, WithdrawManager and price manager.                   |
| `TECH_CONTEXT_MANAGER_ROLE`                                                | ContextManager; sets and clears the effective sender context on approved components.                          |
| `TECH_WITHDRAW_MANAGER_ROLE`                                               | WithdrawManager; transfers request-fee shares through the vault base.                                         |
| `TECH_MANAGEMENT_FEE_MANAGER_ROLE` and `TECH_PERFORMANCE_FEE_MANAGER_ROLE` | FeeManager; configures the corresponding vault fee.                                                           |
| `TECH_VAULT_TRANSFER_SHARES_ROLE`                                          | FeeManager; permits its required vault share transfers before transfers are made public.                      |
| `TECH_REWARDS_CLAIM_MANAGER_ROLE`                                          | RewardsClaimManager; invokes vault reward claims and configures the vault's RewardsClaimManager address.      |
| `IPOR_DAO_ROLE`                                                            | The fee recipient from the selected creation package; may update the DAO fee-recipient address in FeeManager. |

The concrete assignments are generated by `_generateAccountToRoles`, and the
allowed target selectors by `_generateRoleToFunction`, in
[`IporFusionAccessManagerInitializerLibV1.sol`](../contracts/vaults/initializers/IporFusionAccessManagerInitializerLibV1.sol).
Do not replace these code-derived assignments with assumptions about deployed
holders.

## Administrators and role changes

`IporFusionAccessManager` inherits OpenZeppelin AccessManager. The initializer
explicitly makes `OWNER_ROLE` self-administered; Owner administers Guardian,
Atomist and Pre-hooks Manager; Atomist administers Alpha, Fuse Manager,
Whitelist and the specialist operator roles. Fee technical roles and the
ContextManager technical role are self-administered; RewardsClaimManager's
technical role is administered by `ADMIN_ROLE`; `IPOR_DAO_ROLE` is
self-administered. Roles without an explicit override retain AccessManager's
zero-valued default administrator, `ADMIN_ROLE`.

Consequently, “vault owner” is a role, not Solidity `Ownable` ownership, and it
is not interchangeable with either the factory admin or vault `ADMIN_ROLE`.
`grantRole` and `revokeRole` are authorized using the configured administrator
of the role being changed. The customized `grantRole` additionally rejects an
account execution delay below the stored minimum for that role. These rules are
implemented in [`IporFusionAccessManager.sol`](../contracts/managers/access/IporFusionAccessManager.sol)
and its generated administrator mappings; the repository pins the inherited
OpenZeppelin behavior in [`package-lock.json`](../package-lock.json).

The default factory flow grants only the following externally controlled or
package-derived vault roles:

- `OWNER_ROLE` to `owner_` for both `clone` and `cloneSupervised`;
- `ADMIN_ROLE` to the direct caller only for `cloneSupervised`;
- `IPOR_DAO_ROLE` to the selected package's fee recipient.

The remaining human/operator arrays are empty in
[`FusionFactoryLogicLib.setupFinalConfiguration`](../contracts/factory/lib/FusionFactoryLogicLib.sol),
so their membership must not be inferred from the role map.

## Two different kinds of delay

### Role execution delay and scheduling

The generated selector mappings and initial account grants use zero execution
delay. The Owner may call the vault's
`setMinimalExecutionDelaysForRoles`, which forwards through the vault's
technical role to the AccessManager. This stored value is a **minimum for later
`grantRole` calls**; setting it does not itself rewrite existing memberships.
An account granted a nonzero execution delay cannot call the protected selector
immediately: it schedules the exact caller, target and calldata in AccessManager,
waits until the operation is ready, and then executes/consumes that schedule.
Guardian or Admin can cancel eligible scheduled operations.

The floor storage and grant check are in
[`RoleExecutionTimelockLib.sol`](../contracts/managers/access/RoleExecutionTimelockLib.sol)
and [`IporFusionAccessManager.sol`](../contracts/managers/access/IporFusionAccessManager.sol);
the Owner-to-vault and vault-to-AccessManager selector assignments are in the
initializer. OpenZeppelin AccessManager's inherited scheduling implementation is
pinned to version `5.0.2` by [`package.json`](../package.json) and
[`package-lock.json`](../package-lock.json).

### Redemption delay

`redemptionDelayInSeconds_` is separate from role scheduling. The factory passes
it to the new AccessManager; the AccessManager accepts values from zero through
seven days. A deposit, mint or permit deposit sets the share receiver's unlock
timestamp. Until that timestamp, the account cannot withdraw, redeem, transfer
or be the share owner in `transferFrom`. This delay protects token flows and
does not grant, revoke or administer a role.

The bound is enforced by
[`IporFusionAccessManager.sol`](../contracts/managers/access/IporFusionAccessManager.sol),
and the affected selectors and per-account lock are implemented in
[`RedemptionDelayLib.sol`](../contracts/managers/access/RedemptionDelayLib.sol).

## Checklist before an operational call

1. Identify the exact factory or vault deployment and matching ABI; source code
   in this checkout does not prove deployed identity.
2. Name the direct transaction caller, requested `owner_`, factory role holder
   and resulting vault role holder separately.
3. For creation, query the fee package list under the exact direct factory
   caller and record the selected index, values and recipient.
4. For vault actions, query the selector's required role, the caller's role and
   execution delay, target closed status, and any pending schedule.
5. Check redemption lock state separately from permission and execution delay.
6. Record network, addresses and block for every live-state observation. Never
   infer current holders from this document or from factory initialization code.
