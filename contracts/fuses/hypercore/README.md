# HyperCore fuses (IL-8416)

This package lets a Fusion vault on HyperEVM manage its **own** HyperCore account through delegatecalled fuses. The vault remains the CoreWriter sender; no external position manager, API wallet, or sub-account receives control of its assets. Market ID is `HYPERCORE = 55`.

## Supported surface

- EVM→Core deposit of a granted spot token through its verified route: Circle USDC uses the CoreDepositWallet, while an explicitly generic linked ERC20 may use a direct system-address transfer. The first deposit may activate the Core account.
- CoreWriter 1 (perp limit order), 6 (spot send), 7 (USD class transfer), 10/11 (cancel), 12 (builder fee approval), and 13 (send asset), each through a typed fuse. No raw action entry point.
- Standard account mode, native perp dex 0 and the vault's configured HIP-3 perp dexes (see "HIP-3 builder-deployed perp dexes" below), all with USDC collateral, granted spot tokens and granted perp assets only. No spot orders, sub-accounts, vault transfers, staking, API wallets or unified-mode accounting in v1.

The Atomist grants `SpotToken`, `SendCap`, `PerpMarket`, `PerpPositionCap`, `Destination`, `Builder`, and `Config` substrates. Grants are capability limits, not a promise that a CoreWriter action will execute: HyperCore may reject an action after the EVM transaction succeeds. A sell order whose `sz × max(limitPx, markPx)` exceeds the `PerpMarket` cap reverts with `HyperCoreOrderFuseExceedsMaxNotional(notionalUsd6, maxNotionalUsd6)`; a sell on a market whose mark price reads zero reverts with `HyperCoreOrderFuseMarkPriceUnavailable(readIndex)`. The Atomist must keep the spot-token list complete for assets the vault can hold; an unlisted token is not included in this market's NAV. For a direct-linked token, the grant uses the Core token's ERC20; for Circle USDC the grant uses the ERC20 returned by the Core deposit wallet's `token()`. Native HYPE uses an explicitly configured oracle key for NAV and is not ERC20-depositable. Token indexes are network-specific (on the public testnet, token 150 is not HYPE).

For Core token 0 on mainnet, `tokenInfo(0).evmContract` is Circle's **CoreDepositWallet**, not an ERC20. Its `token()` is native Circle USDC on HyperEVM. The grant's `evmAsset`/oracle key is that ERC20; deposits must approve and call the wallet's `depositFor(vault, amount, spotDex)` route, then revoke allowance. Never send this USDC ERC20 directly to `0x2000…0000`: that address is the Core→EVM system route. The first inbound credit to a new Core account is charged a one-time activation fee: on mainnet HyperCore deducted 1 USDC while the wallet's `newCoreAccountFee()` read 0, and that wallet fee is governance-controlled and may add to it. The cached value is still the gross in-transit credit, so it overstates an activating deposit by the fee until the first live refresh, but settlement no longer relies on time: the deposit stays pending until the vault's Core spot balance reaches `baseline + credit − allowance`, where the allowance (`Config{ActivationFeeAllowanceUsdcWei}`, default 1 USDC in Core wei, USDC first deposit into a not-yet-activated account only) nets the activation fee. A dust donation that merely activates the account therefore does not settle the deposit. Check the activation delta against the Core ledger during the first live deposit; a larger fee (e.g. a raised wallet `newCoreAccountFee()`) needs a higher allowance or the deposit settles only at the timeout. The local simulator's old direct-transfer USDC path is not proof of this mainnet route; use its wallet-path regression tests and then bounded live M0 evidence.

Grant changes are the Atomist's responsibility. Revoking a `SpotToken` while the Core account still holds it removes that asset from this market's computed NAV; remapping its oracle key can misprice it. Duplicate grants for one token index with different oracle keys are order-sensitive and may silently alter pricing. Close/transfer the position before revocation, reject conflicting token-index mappings in the deployment review, and verify metadata/feed mapping before granting. The balance fuse does not add fail-closed checks for the consequences of grant edits. The same applies to `Config{PerpDexIds}` and `PerpMarket` grants for HIP-3 markets; see "Grant changes for HIP-3 dexes and markets" below.

## HIP-3 builder-deployed perp dexes

Besides native perp dex 0, the fuses support the following USDC-collateral, builder-deployed HIP-3 perp dexes on HyperEVM mainnet (chain id 999):

| Dex  | Index | Bit value in `PerpDexIds` |
|------|-------|----------------------------|
| xyz  | 1     | 2                          |
| abcd | 6     | 64                         |
| para | 8     | 256                        |
| mkts | 9     | 512                        |
| io   | 10    | 1024                       |

`HyperCoreSupportedDexLib.isSupportedPerpDex` and `HyperCoreSupportedDexLib.supportedHip3DexMask` are the source of truth for this set. HIP-3 dexes whose collateral token is not USDC (for example ones collateralized in USDH, USDE, or USDT0) are not supported and are rejected by the contracts. On any chain other than 999, `supportedHip3DexMask()` returns zero and no HIP-3 dex is supported at all.

A HIP-3 perp market is identified differently depending on where the identifier is used. For the third market of dex `xyz` (`xyz:NVDA`, index 2 within the dex):

| Use                                                                                   | Identifier                                             | `xyz:NVDA` |
|----------------------------------------------------------------------------------------|---------------------------------------------------------|------------|
| CoreWriter order and cancel payloads, the `PerpMarket` substrate, fuse call inputs      | action asset = `100000 + dex * 10000 + indexInDex`       | 110002     |
| Read precompiles (position, mark price, oracle price, asset metadata)                  | read index = `dex * 10000 + indexInDex`                  | 10002      |
| `accountMarginSummary`                                                                  | perp dex index                                          | 1          |

`HyperCoreAssetIdLib.isHip3Asset`, `perpDexOf`, and `readIndexOf` implement this mapping (native markets use the action asset unchanged as the read index, since `dex == 0`). A read precompile called with the action asset of a HIP-3 market addresses a different index than intended: it reverts when no market exists at that index, and returns another market's data when one does. The best-bid-offer precompile is the exception and takes the action asset directly. The precompiles ignore any calldata words beyond what they expect, so the dex and the in-dex index must always be passed as a single combined identifier, never as two separate arguments. `HyperCoreLib.position2` reads precompile `0x813` and must be used for position reads of HIP-3 markets, because the legacy position precompile `0x800` cannot address read indices above 65535 (dex 7 and above); NAV itself does not read positions at all — it prices each dex through `accountMarginSummary`. The order fuse reads the mark price of a HIP-3 market through the same read-index mapping (`readIndexOf(actionAsset)`) when admitting a sell. Raw mark/oracle prices from the precompiles carry `6 - szDecimals` decimals; `HyperCoreLib.perpPxToPx1e8` converts them to the 1e8 scale of CoreWriter `limitPx`.

The single-market rule constrains order admission only. If any `PerpMarket` substrate granted to the vault is a HIP-3 market, the order fuse (`HyperCoreOrderFuse`) requires that exactly one `PerpMarket` substrate is granted in total; `enter` reverts with `HyperCoreOrderFuseSingleMarketRequired(count)` otherwise. Nothing stops the Atomist from granting several `PerpMarket` substrates including a HIP-3 one anyway; new orders are then rejected until exactly one `PerpMarket` grant remains, but cancels stay available for every granted market on a supported and configured dex, so resting orders can still be cancelled while the market set is being changed. Vaults that only trade native markets may keep several `PerpMarket` grants without triggering this rule at all. An order whose asset's dex is not in the supported set reverts with `HyperCoreOrderFuseUnsupportedPerpDex(dex)`; an order on a supported dex that is not enabled in the vault's `PerpDexIds` config reverts with `HyperCoreOrderFusePerpDexNotConfigured(dex)`.

The cancel fuse (`HyperCoreCancelFuse`) requires the asset being cancelled to be granted as a `PerpMarket` substrate on a perp dex that is both in the supported set and enabled in the vault's `PerpDexIds` config: an unsupported dex reverts with `HyperCoreCancelFuseUnsupportedPerpDex(dex)`, an unconfigured dex with `HyperCoreCancelFusePerpDexNotConfigured(dex)`.

The send fuse (`HyperCoreSendFuse`) applies the same dex admission rule to both the source and destination dex of any transfer leg: a dex that is neither spot nor the native perp dex, and is not supported or not enabled in the vault's `PerpDexIds` config, reverts with `HyperCoreSendFuseUnsupportedDex(dex)`. Any leg where the source or the destination dex is a HIP-3 dex must be a self-send (destination is the vault itself) of token 0 (USDC): a destination that is not granted reverts with `HyperCoreSendFuseDestinationNotGranted(destination)`; a granted destination other than the vault itself reverts with `HyperCoreSendFuseUnsupportedBridgeRoute(sourceDex, destinationDex)`, because only a spot-to-spot route may leave the vault's account and a HIP-3 leg never is spot-to-spot; a token other than USDC reverts with `HyperCoreSendFuseUnsupportedToken(tokenIndex)`. Transfers between spot and a configured dex, between the native dex and a configured dex, and between two configured dexes are all allowed this way. When the source dex is a HIP-3 dex, the requested amount (Core-wei, converted to USD with 6 decimals and rounded up) is compared against the positive `accountMarginSummary(sourceDex).accountValue` of that dex; zero or negative equity, or equity below the required amount, reverts with `HyperCoreSendFuseInsufficientDexEquity(dex, availableUsd6, requiredUsd6)`. A native-dex source still uses the native `withdrawable` check and a spot source the available spot balance, unchanged from native-only transfers. Passing the equity check is not a guarantee that HyperCore accepts the transfer: HyperCore applies its own margin rules on top and can still reject it.

## Configuring a vault for a HIP-3 market

- `Config{PerpDexIds}` is a bitmap where bit `i` enables perp dex `i`; bit 0 must stay clear, since the native dex is always included regardless of this config. An absent or zero config makes the vault native-only. `HyperCoreSubstrateLib.getPerpDexBitmap` validates the whole configured bitmap, not only the bit being queried: with an unsupported bit set, live valuation reverts with `HyperCoreUnsupportedPerpDexConfig`, and because every action fuse values the account before sending its CoreWriter action, no new HyperCore action can be sent either while that bit stays set. Depending on which check runs first, the error a caller actually sees can instead be the fuse's own unsupported-dex error. Example: an xyz-only vault sets this value to `2`.
- Trading a HIP-3 market needs one `PerpMarket` substrate granted with the market's action asset (for `xyz:NVDA`, `110002`). As noted above, granting any HIP-3 `PerpMarket` restricts the vault to exactly that one `PerpMarket` grant; vaults with only native markets may keep several.
- Collateral route: EVM USDC → Core spot (deposit fuse) → the target dex (send fuse, action 13, self-send, token 0) → trade → back the same way. Moving collateral into a dex that is already enabled in `PerpDexIds` needs no `PerpMarket` grant by itself. The margin fuse (action 7, USD class transfer) only moves collateral between spot and the native dex; it does not reach HIP-3 dexes.
- Before granting a dex or market, verify off-chain that the dex index still maps to the expected dex name and that its collateral token is USDC (Hyperliquid `/info` `perpDexs` and `meta` endpoints), and verify the exact market name for the action asset being granted.
- Dex `abcd` (index 6) is supported by the contracts, but at the time this was last checked no account with a non-zero balance was found on it, so its valuation path could not be observed against non-zero state. Before enabling bit 6 on a vault, verify the equity identity on non-zero state: read `accountMarginSummary(6, account)` together with that account's positions and mark prices in one call, check that `accountValue = rawUsd + sum(position size × mark price)`, and compare the result with the Hyperliquid API.

## NAV and pending actions

Live Core NAV is the sum of each granted spot token's `spotBalance.total` (including holds) priced by the vault oracle, plus signed `accountMarginSummary.accountValue` for native perp dex 0 and for every HIP-3 perp dex enabled in the vault's `PerpDexIds` config. `accountValue` of a dex is that dex's complete equity — collateral, cross and isolated positions at mark price, funding and fees — in USD with 6 decimals; positions are never added a second time on top of it. A dex whose bit is clear in `PerpDexIds` is never read. The market excludes EVM-side balances, which the vault accounts for separately. The balance fuse returns USD WAD. A negative aggregate is an error, not zero. A failed read of a configured dex makes the whole valuation revert.

Only one HyperCore deposit/CoreWriter action may be pending per vault (orders and cancels create no pending record, see below). While it is pending, the balance fuse returns a cached Core value: for an EVM→Core deposit that cache includes the in-transit credit so the underlying debit is offset; for a Core→EVM send to a token system address it subtracts the oracle-valued outgoing amount. The latter makes the public stored NAV conservatively low in the enqueue block before the EVM credit; for linked underlying USDC the EVM credit normally offsets it from H+1, subject to fees and the live timing gate. Non-underlying ERC20 balances can remain stale until the market-55→market-7 dependency refresh. Share-priced entry points block while pending and refresh market 55 when safe, so the temporary public view is not used for mint/redemption pricing. An `execute`/external balance-refresh hook blocks operations that would consume pending NAV. Do not deploy these UpdateBalances-style pre-hooks through ContextManager: its sender semantics are incompatible (IL-8310). The vault must have the role required for the hook's self-call to `updateMarketsBalances([55])`.

**Pre-hook deployment checklist (IL-8529).** Install `HyperCoreCapitalFlowPreHook` on exactly the six share-priced selectors (`deposit`, `depositWithPermit`, `mint`, `withdraw`, `redeem`, `redeemFromRequest`) and `HyperCorePendingActionPreHook` on `execute` and `updateMarketsBalances`. A hook run under a selector it is not meant for reverts with `HyperCorePreHookWrongSelector(selector)` (CapitalFlow on `execute`/`updateMarketsBalances` would recurse; PendingAction on a share-priced flow would skip the pre-pricing refresh). `HyperCorePendingActionPreHook` is parameterless and has no caller exception (IL-8543): while a transfer is pending, `execute` and `updateMarketsBalances` revert for every caller. A missing or foreign hook on a flow selector runs no HyperCore code, so hook code cannot detect it; the action fuses do instead. `HyperCoreDepositFuse.enter` and non-reduce-only orders in `HyperCoreOrderFuse` revert with `HyperCorePreHooksNotWired(selector, implementation)` unless all six share-priced selectors point at one hook that exposes the CapitalFlow marker `HYPERCORE_CAPITAL_FLOW_PRE_HOOK_ID()` (the marker, not a fixed address, so a new CapitalFlow version needs no fuse redeploy). Reduce-only orders, margin, send, cancel and builder-fee actions are not gated, so a mis-wired vault can still unwind. The gate stops deploy-time mis-wiring before any capital reaches Core, but a re-wiring made after positions are open is not detected: the unhooked selector runs no HyperCore code and only the next gated fuse action fails. That case needs process controls: put `PRE_HOOKS_MANAGER_ROLE` behind a timelock, monitor `PreHookImplementationChanged` on every vault with market 55, and never pause a HyperCore flow selector with `PauseFunctionPreHook` ("unpausing" with `address(0)` leaves the selector unhooked). After deployment: read back `getPreHookImplementation` for all 8 selectors; check `hasRole(UPDATE_MARKETS_BALANCES_ROLE, vault)` with execution delay 0; confirm no flow selector is routed through ContextManager (IL-8310); and never pass a duplicate selector in one `setPreHookImplementations` call (PreHooksLib silently keeps the last value).

Orders and cancels settle **TIMING-only** (IL-8527, IL-8543): they create **no pending record**, so they never block `execute` or user flows and a resting order can be cancelled immediately. A one-Core-block mini-gate remains: after an order the persistent `lastOrderL1Block` is set; user capital flows (deposit/mint/withdraw/redeem/redeemFromRequest, via `HyperCoreCapitalFlowPreHook`) revert with `HyperCoreOrderInFlight` until a later Core L1 block, and at most one order per Core L1 block is accepted (`HyperCoreOrderRateLimited`). Cancels neither rate-limit nor set the gate. An order or cancel is still refused while a transfer is pending. This is an operational assumption, **not proof** the queued action executed or was rejected: Hyperliquid documents a delay of a few seconds but no maximum. A late IOC or cancellation can change exposure after share pricing. The `PerpMarket` cap bounds the initially submitted notional — `sz × limitPx` for buys, `sz × max(limitPx, markPx)` for sells, with the mark price read from precompile `0x806` at admission because a sell's limit is only a price floor — **not** the later loss on an open perp position, and not a move of the mark price between admission and Core execution. Use only after explicit Atomist risk approval; verify cancels independently through Hyperliquid order status. `HyperCorePendingReader.isOrderInFlight()` and `pendingState().state.lastOrderL1Block` expose the gate.

A resting GTC order can fill after its placement was settled; the fill is included in NAV only at the next refresh, and every priced vault operation refreshes market 55.

**Config keys `SettlementMode` and `WindowOrderSeconds` are reserved and ignored (IL-8543).** The `ConfigKey` enum positions are unchanged, so a vault that already holds these grants still decodes its configuration, but no fuse reads them: any value (including one the removed validation would have rejected) is accepted and orders/cancels behave as described above. New vaults should not grant them. The `PendingAction` storage struct keeps its exact field order; the REPORTED-only fields (`deprecatedSettlementMode`, `deprecatedReportedResult`, `deprecatedResultL1Block`, `deprecatedRefreshing`) are never written any more and are only cleared with the record. A legacy record left by an older build settles like any timing record. `HyperCoreActionEnqueued` keeps its signature for indexers (`actionClass` is always 1, `settlementMode` always 0). Fuse id 115 (the removed `HyperCoreSettlementFuse`) is reserved in `FuseTypes` and must not be reused.

**Why REPORTED was removed (IL-8543).** The REPORTED mode (a 2-of-3 observer-signed report via `HyperCoreSettlementReporter`/`HyperCoreSettlementFuse`) was meant to prove an order's outcome before pricing resumed. IL-8421 (independent observers and an authenticated Core data source) was rejected: there is no independent observer set and no authenticated data source to build it on. Transfers, the only actions that move value across domains, are proven on-chain by their balance effect (IL-8526). An order fill at the mark price is NAV-neutral, and the remaining price-source risk is covered by the mark-vs-oracle band and the position cap (IL-8534).

Transfer-class actions use the documented H+1 ordering only after the live M0 gate proves linked-token debit/credit visibility in the target environment. A successful EVM receipt alone is not a Core execution receipt.

Effect-based settlement (IL-8526): only the two flows whose value is "in the void" between domains wait for their cross-domain effect, in addition to the time window and a later L1 block: the EVM→Core deposit (settles when the vault's Core spot balance of the token reaches the snapshotted `expectedBalance`, read as `coreUserExists && spotBalance.total >= expected`) and the Core→EVM bridge (`enterSpotSend`/`enterSendAsset` to the token system address; settles when the vault's balance of the granted SpotToken ERC20 reaches `baseline + exact EVM amount`). Margin moves (spot↔perp), self-sends between dexes and builder-fee approval are atomic inside Core and keep settling by time (orders and cancels create no record). `HyperCorePendingLib.isEffectObserved()` exposes the predicate; `HyperCorePendingReader.pendingState()` returns the effect fields in `state`. Transfers settle on their effect (IL-8526), independent of any legacy `SettlementMode` grant (IL-8528, IL-8543).

Timeout and residual risk: after `pendingUntil + Config{TransferTimeoutSeconds}` (default 600 s, must be 60..`type(uint64).max`; values below the 60 s floor `MIN_TRANSFER_TIMEOUT_SECONDS` revert with `InvalidTimeout`) the gate opens even if the effect never landed, so a rejected transfer cannot freeze the vault; NAV is then read live and shows the real loss. If Core is merely lagging beyond the timeout, live NAV misses the in-transit amount and shares are mispriced until the credit lands: the GUARDIAN must pause the vault in that case, and the timeout should be sized above the worst observed Core latency. Config keys added by this change (appended, existing key values unchanged): `TransferTimeoutSeconds`, `ActivationFeeAllowanceUsdcWei` (any value fitting `uint64`), since IL-8533 `MaxNavJumpBps`, and since IL-8534 `MaxMarkOracleDeviationBps`. Since IL-8526 `WindowTransferSeconds` is only a minimum wait (pricing safety comes from the observed effect and the timeout), so a short window no longer opens the gate early (IL-8532).

Settlement latch (IL-8518): the first capital flow, `execute`, `updateMarketsBalances` or refresh after a transfer's settlement condition holds latches it. Both pre-hooks call `HyperCorePendingLib.settleIfReady()` before their pending check; it clears the record (keeping `actionNonce` and `lastOrderL1Block`) and emits `HyperCoreActionSettled(nonce)`. Later balance changes, for example a user redeem lowering the EVM USDC balance after a Core→EVM bridge settled, therefore cannot re-open the pending state. `HyperCoreActionSettled` marks the end of every action on-chain; `clear()` remains available and reverts unless the record is settled.

For Core→EVM, action 13 uses the token's exact system address and a spot→spot route. The same Destination grant would otherwise permit action 6, so `spotSend` to a system address additionally requires explicit `Config{SpotSendBridgeEnabled=1}`; it is disabled by default. Set that flag only after M0 proves action 6 credits the vault's EVM balance on the target chain. Do not grant a non-system recipient in v1: without sub-accounts there is no other vault-owned Core recipient. The M0 runbook must test actions 6 and 13 separately and record each EVM credit outcome.

### NAV jump circuit breaker (IL-8533)

`HyperCoreValuationLib.liveValueWad` compares every live Core value (USD WAD) with the value stored for market 55 (`getTotalAssetsInMarket`, converted to USD WAD through the vault's price oracle for the underlying asset) and reverts with `HyperCoreNavJumpExceeded(storedWad, liveWad, maxJumpBps)` when `|live - stored| * 10_000 > maxJumpBps * stored` AND `|live - stored| > Config{NavJumpFloorUsd6}` (absolute tolerance, IL-8766, see below). The check lives in the library, so it protects the balance fuse's live path and every action fuse that snapshots live value into the pending cache (an ALPHA action cannot launder a repriced value through storage). It is skipped while the stored value is zero (first activation, or fully withdrawn). The threshold is `Config{MaxNavJumpBps}` (appended config key, default 5000 = 50%); a configured `0` or a value above `type(uint64).max` reverts with `HyperCoreNavJumpConfigInvalid`, any value in `1..type(uint64).max` is accepted, and a very large value (e.g. `1_000_000`) effectively disables the breaker. A missing oracle price reverts with `HyperCoreNavJumpReferenceUnavailable`.

Transfers do not trip it: while a transfer is pending the cache already includes the in-transit amount and `execute` stores it, so once the transfer settles the live value is approximately the stored value (an EVM to Core deposit that multiplies the Core value, or a Core to EVM bridge of 95% of it, both pass).

It does trip on: a genuine Core value move larger than the threshold between two refreshes; a transfer that Core rejects (the effect never lands, the gate opens on the timeout) whose amount exceeds the threshold (an intended freeze: the stored value includes value that is not on Core); and a precompile semantic change with an unchanged layout (for example `accountValue` reported with extra decimals), which previously repriced the vault silently (PoC: NAV 999,999 to 5,949,999). A third cause is a donation (IL-8766): anyone on HyperCore can `spotSend`/`usdSend` USDC to the vault's Core account, so when the stored value is small (for example after 95% was bridged back to EVM) a donation larger than `MaxNavJumpBps` of the stored value trips the breaker and freezes every deposit, mint, withdraw and redeem, and the manager's refreshes and snapshots, until recovery. The donor loses the funds, so this is griefing, not theft, but it is cheap and repeatable. Mitigation: `Config{NavJumpFloorUsd6}` (appended key 11, USD with 6 decimals, any value up to `type(uint64).max`; a larger value reverts with `HyperCoreNavJumpConfigInvalid`). The breaker only trips when the deviation exceeds BOTH the relative threshold and the floor, so a donation (or drop) up to the floor is accepted and the next refresh books it. The breaker stays two-sided and a deviation above the floor still trips, so a precompile semantic change such as `accountValue` x100 is still caught. The floor applies to every trip cause above (rejected transfers and genuine moves, not only donations): any jump at or below the floor is booked silently on the next refresh instead of freezing. A donation above `max(floor, MaxNavJumpBps * stored / 10_000)` still freezes, so a freeze costs the donor more than the floor. Silently mispriced NAV between refreshes is bounded by `max(MaxNavJumpBps * stored, floor)`. The floor is opt-in: when the key is absent it is 0 and the behaviour is the pure relative check above, so the deployment runbook MUST set it per vault (suggested 0.5-1% of the expected TVL; vault sizes differ by orders of magnitude, so there is no safe code default).

Recovery: GUARDIAN pauses meanwhile; the FUSE_MANAGER (`grantMarketSubstrates` requires `FUSE_MANAGER_ROLE`) grants a higher `MaxNavJumpBps` (re-granting the full substrate list), a refresh stores the new value, then the FUSE_MANAGER restores the threshold. `HyperCorePendingReader` does not call `liveValueWad`, so reads of the pending state are unaffected.

An empty or invalid precompile reply deliberately keeps failing closed with `HyperCorePrecompileFailed`: the vault cannot be priced, so user flows stay frozen until the precompile answers again.

#### Deploying `NavJumpFloorUsd6` (IL-8766)

Builds without the key revert `HyperCoreInvalidConfigKey` on it (`getConfig` decodes every config substrate), so the order is: (1) deploy the full new HyperCore set and swap it in: the balance, deposit, margin, order, cancel, send and builder-fee fuses (all seven) plus `HyperCoreCapitalFlowPreHook` (the library is compiled inline into each; the order and cancel fuses decode the config through `isPerpDexConfigured`, the capital-flow hook through `checkMarkOracleBand`). `HyperCorePendingActionPreHook` and `HyperCorePendingReader` decode no config and need no redeploy; (2) re-register the capital-flow hook on its six selectors; (3) only then grant `Config{NavJumpFloorUsd6}` (re-granting the full substrate list, FUSE_MANAGER). Granting key 11 while ANY old-build fuse (including order and cancel) or the old capital-flow hook is still attached makes it revert `HyperCoreInvalidConfigKey(11)`: orders and cancels stop working, so the manager can neither close perps nor cancel resting orders, and user flows through the hook freeze. Follow-up in the vault-validator repo: `HyperCoreKnownFuses.sol` needs the new build and the config decoder in `HyperCoreMarketValidator` needs the new key.

#### Precompile layout change runbook

If Hyperliquid changes a precompile layout: (1) pause the vault via GUARDIAN; (2) redeploy every contract importing `HyperCoreLib` / `HyperCoreValuationLib`: the action fuses (deposit, margin, order, cancel, send, builder fee), the balance fuse, both pre-hooks and the pending reader; (3) swap them in through governance; (4) verify the new reads against the Hyperliquid API; (5) unpause.

### Mark price band and position cap (IL-8534)

NAV prices perp accounts through `accountMarginSummary.accountValue`, i.e. at the Core mark price, and the mark of a thin book (especially a HIP-3 dex) can be pushed. Reviewer PoC: with a 1000 HYPE position an attacker deposits 500,000 at the fair NAV, the mark moves +20%, and the attacker redeems 502,666.68 (+2,666.68) at the pushed mark. Two limits address this.

**Mark vs Core oracle band (share-priced flows).** `HyperCoreValuationLib.checkMarkOracleBand` (after the `PerpDexIds` validation and the unactivated-account short-circuit, so it only runs when the Core account exists) walks the market's `PerpMarket` substrates. For every granted market on which the vault holds a non-zero position it reads `markPx` (0x806) and `oraclePx` (0x807) at the market's read index and reverts with `HyperCoreMarkOracleDeviation(asset, markPx, oraclePx)` when `|mark - oracle| * 10_000 > maxBps * oracle` (an oracle of zero reverts the same way). Both prices share the raw precompile scale, so no conversion is needed. The position read is `position` (0x800) for native markets and `position2` (0x813) for HIP-3 markets, at `readIndexOf(asset)` (`dex * 10000 + index`, never the `100000 + ...` action asset); the error reports the action asset. A market without a position costs one position read and is skipped; a HIP-3 market is only read when its dex is enabled in `Config{PerpDexIds}` (the same dexes NAV values), and asset ids outside the native/HIP-3 space are ignored. The threshold is `Config{MaxMarkOracleDeviationBps}` (appended config key, default 500 = 5% when unset); a configured `0` or a value above `type(uint64).max` reverts with `HyperCoreMarkOracleBandConfigInvalid(value)`. The band guards share-priced flows only: `HyperCoreCapitalFlowPreHook` calls `HyperCoreValuationLib.checkMarkOracleBand(marketId)` after its pending checks and before the market refresh, so deposit, depositWithPermit, mint, withdraw, redeem and redeemFromRequest revert while mark and oracle diverge (the check is a no-op until the Core account exists). `execute`, `updateMarketsBalances`, refreshes, TIMING orders and cancels are NOT blocked, so the manager can de-risk (close positions, cancel orders) exactly while prices diverge. Trade-off: a manager action during divergence may store a mark-based market-55 value, but user flows stay blocked by the band until mark and oracle converge, and the IL-8533 NAV jump breaker (in `liveValueWad`) still applies everywhere. The band does not protect against a HIP-3 dex operator, who sets the oracle: operator trust is accepted explicitly (see HIP-3 risks).

**Aggregate position cap (order fuse).** `PerpMarket.maxNotionalUsd6` bounds a single order only, so repeated orders could still build an arbitrarily large position. The appended substrate type `PerpPositionCap` encodes `(uint32 asset, uint88 maxPositionNotionalUsd6)` (`encodePerpPositionCap` / `decodePerpPositionCap` / `getPerpPositionCap(marketId, asset)`). The cap is optional: when none is granted for an asset behaviour is unchanged and only the per-order cap applies; a duplicate cap for the same asset is rejected with `HyperCoreInvalidSubstrate` (same policy as `SendCap`). In `HyperCoreOrderFuse` (before sending) the fuse reads the vault's current position size, converts the order size from the 1e8 order scale to the position's `szDecimals` units (`sz / lotOf(szDecimals)`, exact because the lot check runs first), assumes a full fill (`szi + sz` for buys, `szi - sz` for sells) and values the post-order `|size|` at the order's admission price (`limitPx` for buys, `max(limitPx, markPx)` for sells, the same basis as the per-order cap, rounded up). It reverts with `HyperCoreOrderFusePositionCapExceeded(asset, positionNotionalUsd6, capUsd6)` when that notional exceeds the cap AND the order increases `|size|`. An order that keeps or reduces `|size|` is always allowed, even above the cap and even when it flips the side, so de-risking is never blocked. Known limitation: resting GTC orders are not visible on-chain and are not counted, so a cap bounds position plus the single order being admitted, not the sum of resting orders.

**Not implemented and why.**

- Independent external price reference (middleware, Chainlink or Pyth per perp market): the vault's price oracle middleware on HyperEVM has no feeds for perp underlyings or HIP-3 equities, perp markets have no ERC20 key for the middleware, and sourcing and governing such feeds is a separate integration. The Core oracle is the best on-chain reference available today and is independent of the order book; it does not protect against a HIP-3 dex operator, who sets that oracle (operator trust is accepted explicitly, see HIP-3 risks).
- Tight NAV jump limit: implemented in IL-8533 with a 50% default to catch gross valuation errors. A threshold tight enough to catch a 0.5% NAV move would block normal operation of a leveraged vault, so small manipulations are handled by the band and the position cap instead.
- Off-chain mark-vs-reference monitoring with automatic GUARDIAN pause: operational tooling outside this repository, not part of this change.
- Recommendation for HIP-3 vaults: size `PerpPositionCap` from an off-chain depth assessment and use a withdrawal request delay (WithdrawManager) so a redemption cannot be timed to a manipulation.

## Grant changes for HIP-3 dexes and markets

Clearing a bit in `Config{PerpDexIds}` while the account still has collateral, a position, or resting orders on that dex removes that dex's signed equity from NAV entirely; depending on the sign of that equity, NAV then reads too high or too low. Before clearing a bit: cancel resting orders on that dex, close the position, move the collateral back to spot, wait until pending actions are settled, and only then clear the bit. If a bit was cleared by mistake, set it again before trying to cancel or transfer on that dex: cancels and transfers for a dex whose bit is clear are rejected while the bit stays clear.

Revoking a `PerpMarket` grant stops new orders and cancels for that market but does not remove its dex from NAV; the dex's equity keeps being counted as long as the dex's bit stays set in `Config{PerpDexIds}`. Cancel resting orders on a market before revoking its `PerpMarket` grant.

The contracts do not inspect live positions, resting orders, or account equity when grants change, and do not block a grant change that would leave the account in an inconsistent state.

## HIP-3 risks

- **Dex operator**: the deployer of each HIP-3 dex sets its oracle prices and leverage limits, and can halt a market and settle positions at mark price. NAV uses that same mark price. Enabling a dex means accepting its operator as a trusted party for that dex's markets.
- **Leverage**: the default leverage of an account equals the market's configured maximum, and CoreWriter offers no action to change leverage or to add isolated margin, so the vault cannot adjust either.
- **Isolated-only markets**: on markets flagged isolated-only, the position is margined in isolation at the default leverage and can be liquidated after a move of only a few percent, even while the vault holds idle collateral on the same dex. As measured, this applied to xyz's EWY, PLTR, SOXL, CRCL, INTC, and HOOD markets (for example, a long entered at 148.37 had a liquidation price of 140.52, 5.3% below entry), and to most markets on para and io. A vault holding a position on such a market does not behave like an unleveraged holding of the underlying stock.
- **Market hours**: stock perps are priced by the dex operator's oracle continuously, including outside the underlying exchange's trading hours.
- **Liquidity**: as measured, para, mkts, and io each had roughly 1–2% of xyz's daily volume.
- **Donations**: anyone can send USDC to the vault's HyperCore account, to spot or to a perp dex. Such a transfer raises NAV only where the vault values the balance: on a granted spot token and on the native or a configured HIP-3 dex. A balance on a dex that is not enabled in `PerpDexIds` is not counted. This is the same exposure the vault already has for spot balances. A donation that is large relative to a small stored value can also trip the NAV jump breaker; `Config{NavJumpFloorUsd6}` (IL-8766) bounds that freeze.
- **Order settlement**: unchanged from native markets — see the order-settlement discussion above, including that a resting GTC order can fill after its placement was already settled.
- **Redeployment**: HIP-3 valuation logic is compiled into the balance, order, cancel, margin, send, deposit, and builder-fee fuses. A vault that uses HIP-3 dexes must use the versions of all seven fuses built from this code; mixing them with older versions would cache a NAV that never includes the HIP-3 dexes.

## Deployment and operational gates

Before enabling funds: configure middleware feeds for every granted Core spot token, verify standard account mode, activate the vault's Core account using the token's verified route, grant and test the market 55 balance fuse, install the composite/guard pre-hooks (the deposit and opening-order fuses refuse to run until all six flow selectors carry the CapitalFlow hook, IL-8529), and validate all selectors/roles in the real vault configuration. A Core HYPE reserve, if needed for Core→EVM transfer fees, must be topped up and NAV-priced; it cannot be deposited through the ERC20 fuse. Use the deployment/whitelist and SDK artifacts from M4/M5, not hand-built raw CoreWriter payloads.

`chat/M0.md` and `chat/M0-MAINNET-RUNBOOK.md` record the current **NO-GO** state for a live end-to-end claim: contract activation, H+1 visibility, nonzero-account decimal scales, and CoreWriter reliability need a funded, bounded mainnet-999 probe after the wallet-path fix is tested. The historical testnet node issue reports successful EVM transactions with no Core effect; it does not prove a mainnet outcome. Local mocks or an Anvil fork do not substitute for this gate; Anvil does not natively execute HyperCore precompiles.

Run the suite single-threaded:

```
forge test --match-path 'test/fuses/hypercore/*Test.t.sol' -j 1
```

One existing script test writes files to disk and is not safe to run in parallel or alongside another forge process. The suite mocks the precompiles and CoreWriter and covers encodings, grants, sell-side cap admission at mark price, NAV arithmetic, pending transitions, hooks, and action validation.
