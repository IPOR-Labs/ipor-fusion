# Reward fuses

The fuses in this directory claim rewards on behalf of a PlasmaVault and hand them to its `RewardsClaimManager`.

## How a claim reaches the vesting schedule

A keeper holding `CLAIM_REWARDS_ROLE` calls `RewardsClaimManager.claimRewards`. The manager checks that every fuse in the batch is supported and calls `PlasmaVault.claimRewards`, which runs each fuse by delegatecall. A revert in one fuse reverts the whole batch.

Each fuse claims for the vault at the distributor. The claimed rewards reach the `RewardsClaimManager` either by a transfer the fuse makes or because the fuse names the manager as the receiver. A token on the `MerklClaimFuse` skip list stays in the vault and, if it is the underlying, does not vest.

The manager counts the underlying token it holds in `balanceOf()`, and the vault adds that value to `totalAssets()`. With `vestingTime` set to zero, `balanceOf()` is the current underlying balance of the manager. Otherwise it is the linearly vested part of the balance recorded at the last `updateBalance()`, minus what was already transferred. `updateBalance()` pushes the vested part to the vault and starts a new schedule over what the manager holds at that moment.

A reward token other than the underlying stays in the manager until an account with `TRANSFER_REWARDS_ROLE` moves it with `RewardsClaimManager.transfer`. That function refuses the underlying token.

## Claims made on the vault's behalf

Some distributors accept a claim for an account from any caller and pay the account itself. Such a claim does not go through the `RewardsClaimManager`. The tokens arrive in the vault, they are not vested, and no fuse in this directory moves a balance the vault already holds: every fuse forwards the result of its own claim, the increase of a token balance across its own call, or an amount it read before the claim. For the underlying token the effect on the vault is described in [Reward vesting and rewards claimed on the vault's behalf (IL-9744)](../vaults/README.md#reward-vesting-and-rewards-claimed-on-the-vaults-behalf-il-9744).

Absence from the first list below does not mean that vesting is guaranteed. Before the vault takes a position that earns rewards in its underlying token from a distributor, check how that distributor treats claims made for the vault; leaving the claim fuse out does not avoid the exposure.

Where the table says "per the published source", the statement comes from the published source of the protocol, checked 2026-11-16; a deployed instance can differ, and deployed instances were not checked.

## When someone else already claimed

A batch is all or nothing, so a fuse that reverts stops the claims of every other fuse in the same batch.

- **Morpho.** Per the published source of the protocol (checked 2026-11-16; a deployed instance can differ), the distributor rejects a claim that adds nothing beyond the amount already claimed, so the entry reverts. The keeper must simulate the batch, leave out that entry and send the rest. The entry returns to the batch when the distributor publishes a higher cumulative amount. A revert of an exhausted entry is not a failure of the distributor.
- **Moonwell.** Per the published source of the protocol (checked 2026-11-16; a deployed instance can differ), the call does not revert. The fuse forwards what its own call pays, which is zero only when nothing more is payable.
- **Compound V3.** Per the published source of the protocol (checked 2026-11-16; a deployed instance can differ), the call ends without a transfer when nothing is owed, so it does not revert. `claimTo` sends to the manager what is owed at the moment of the call. The emitted event carries no amount and does not prove that a transfer happened.

For all three, the fuse does not move a balance the distributor paid to the vault earlier. If the token is the underlying, it is already part of `totalAssets()`; any other token stays in the vault, see the section linked under "See also". Rewards that accrue afterwards are collected by an ordinary claim. That is different from retrying an exhausted entry.
